# 作者提示词

把下面分隔线之间的**全部内容**粘给 Claude / GPT / Gemini，末尾附上你的行程需求。

产出存成 `apps/web/public/data/<trip-id>/plan.md`，然后 `pnpm data:check`。

---

你要写一份 **TripMD** 格式的旅行计划。这是一种既能给人读、又能被程序确定性解析的 Markdown。

## 铁律

1. **每个 `###` 事件下面必须紧跟一个 ` ```trip-event ` 块。** 漏一个就解析失败。
2. **事件的 `time` 是「到达该地点、开始活动」的时刻，不是出发时刻。** 路上耗时由**上一个事件**的 `to_next` 承担，所以上一个事件必须**提前 travel 分钟结束**。这是最容易写错的地方。
3. **坐标不确定就别写。** 瞎编的经纬度比没有坐标糟得多。只给你确信的知名地标写坐标；餐厅、民宿、小众观景台一律留空。
4. **同一地点全文用完全一致的名称。**
5. 机器字段只放在 ` ```trip-* ` 块里；块外的正文写给人看，随便用粗体、列表、⚠️、表格。

## `trip-event` 字段

| 字段 | 必需 | 值 |
|---|:--:|---|
| `time` | ✓ | `18:25–18:55` / `"13:11"`（点，时长为 0，**要加引号**）/ `morning`·`afternoon`·`evening`·`night`·`allday` |
| `category` | ✓ | 见下表 |
| `place` | | 地点名，须与地点表完全一致 |
| `flags` | | `[warning, tentative, optional, needs-booking]` |
| `cost` | | 自由文本，如 `约 $70/人`、`$49 × 2 = $98`、`$250–400`。程序自动抽金额做预算，写清 `/人` 还是总额；可有可无的加「（可选）」 |
| `booking` | | `{status: required, deadline: 2026-08-01, note: 需提前订位}` |
| `transport` | | **抵达/离开/多目的地间的长途移动必写**（不限飞机）：`{traveler: 谁的（多人汇合时）, mode: flight/rail/drive/ferry/bus, carrier: 承运方, number: 班次号, from, to, dep_time: "10:15", arr_time: "13:11", arr_day_offset: 次日到达写 1, duration: 11h55m（全程含中转）, baggage, stops: [{airport: ICN, wait: 2h10m}]}`。**多人从不同地方出发汇合时写成列表，一人一条**。**不知道的字段直接省略、绝不编造** —— UI 会留「待填」空位 |
| `to_next` | | `{mode, minutes, km, label, note}` |

**类别**（只能用这些，三组十一类）：

**玩**：`sight` 景点 · `outdoor` 户外（徒步/公园/湖）· `viewpoint` 观景（观景台/日落机位/**风景自驾路段**）· `experience` 体验（需买票：缆车/游船/观光飞行）。**吃**：`food` 正餐（含市场小吃）· `cafe` 咖啡甜点 · `bar` 酒吧。**其他**：`flight` 航班 · `transit` 交通 · `lodging` 住宿 · `logistics` 事务（提还车/补货/寄存/进航站楼）

**10 种交通方式**：`walk` `drive` `rideshare` `rail` `bus` `monorail` `streetcar` `ferry` `flight` `bike`

**4 种状态标记**：
- `warning` 有坑，正文里说清楚
- `tentative` 还没定下来
- `optional` 赶不上可以砍
- `needs-booking` 出发前必须预订

## 时间衔接（最容易错，请逐条检查）

```yaml
### 苏扎罗图书馆
time: 15:15–16:03          # ← 16:03 结束，给后面留 12 分钟车程
to_next: {mode: drive, minutes: 12}

### 煤气厂公园
time: 16:15–17:30          # ← 16:15 到达。16:03 + 12 = 16:15 ✓
```

写完每一天，从头核对一遍：**上一个事件的结束时间 + `to_next.minutes` ≤ 下一个事件的开始时间。**

两个特殊情况：

- **事件本身就是移动**（风景自驾、坐轻轨这个动作）→ 把时长写进事件的 `time`，`to_next` 就别再给 `minutes`
- **当天最后一个事件不要写 `to_next`**（没有下一个事件了）。如果要表达"然后去机场"，就把机场作为一个真实事件写出来

## 写好这份计划

结构对了只是能解析。**真正有价值的行程在正文和变体里：**

- **首段是摘要。** 正文第一段（第一个空行前）常显在卡片上，其余折叠。第一段一句话说清最关键的事。
- **抵达和离开要作为第一天第一个、最后一天最后一个事件写出来**，带 `transport` 块（飞机/火车/自驾/轮渡都用它）。多目的地行程中间的长途移动同样写成事件 + `transport`。
- **多人从不同地方汇合**：一个事件里 `transport` 写成列表，每条带 `traveler` 标签，例如她从 PVG 直飞、我从 SNA 飞。
- **正文写「为什么」，不只是「是什么」。** 不是"去 Kerry Park 看日落"，而是"18:15–18:50 金光转粉紫，18:50–19:15 蓝调时刻更出片；山上路边位极少，早到 15 分钟绕圈"。
- **变体（`#### 变体 · 条件`）是这个格式最重要的特性。** 凡是"如果 X 就改成 Y"的判断——天气、排队、季节性关闭、班次取消——都写成变体。这是一份计划最值钱的部分。
- **`fallback_order` 写清赶不上时的砍站顺序。**
- **硬约束写足 `note`。** 尤其是倒推链：为什么必须 11:20 还车。
- **⚠️ 和 🚫 直接写进正文**，标出坑和不建议做的事，并说明理由。
- 备选方案（第二第三选择的餐厅、住宿）写进正文或附录，不要另开事件。

## 租车（有的话）

行程里有租车/长租设备时，加一个 `trip-rentals` 块（任意 `##` 标题下）：

```trip-rentals
- what: 保时捷 Macan
  from: "2026-10-02 11:30"
  to: "2026-10-05 11:20"
  pickup: 唐人街提车点
  dropoff: 唐人街提车点
  note: 加 91+ 号油
```

提车/还车的动作照常写成当天的 logistics 事件，费用写在提车事件的 cost 上。

## 附录

不属于任何一天、但不能丢的内容单独开附录。常见的：`## 附录 · 预算`、`## 附录 · 打包清单`、`## 附录 · 出发前必办`、`## 附录 · 雨天预案`、`## 附录 · 住宿备选`。

每个附录紧跟一个 ` ```trip-ref ` 块声明 `id` 和 `icon`（emoji），其后是自由 Markdown。附录内的小标题用 `###` 或更深（`##` 会被当成新分区）。

- [ ] 每个 `place` 都在地点表里、且拼写完全一致？
- [ ] 只给确信的地标写了坐标？西经和南纬带负号？
- [ ] 当天最后一个事件没有 `to_next`？
- [ ] 至少写了 2–3 个变体？
